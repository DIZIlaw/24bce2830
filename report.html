1. Problem Statement & Project Planning (2 Marks)
1.1 Problem Statement

College students residing inside campus hostels frequently require textbooks, cycles, electronic equipment, lab coats, and hostel furniture. Currently, students rely on unstructured WhatsApp groups, temporary Instagram stories, or external unverified platforms like OLX where strangers outside VIT pose security and fraud concerns. There is a lack of an exclusive, authenticated, relational database management platform to track campus inventories, prevent fraudulent outsiders, manage real-time student negotiations, and maintain verifiable transaction trails inside VIT.

1.2 Objectives & Scope
  • Closed Campus Authentication: Restrict buy/sell interactions exclusively to verified VIT students authenticated via university email and register numbers.
  • Relational Data Integrity: Store, index, and manage products, categories, orders, negotiations, and audit history across a normalized relational database (3NF).
  • Order State Machine: Provide stateful order lifecycle management (Pending → Approved → Completed → Declined) with automated item availability updates.
  • Live Negotiation Threading: Facilitate in-app bargaining between buyers and sellers prior to confirming campus meetup transactions.
  • Scope: Encompasses all academic blocks, Men's Hostels (MH), and Ladies' Hostels (LH) inside VIT campus.

2.4 Database Normalization (Proof of 3NF or Above)

The database has been systematically normalized to Third Normal Form (3NF) to eliminate insertion, update, and deletion anomalies:

  • First Normal Form (1NF): All attributes contain atomic, indivisible values. Multi-valued attributes (e.g., multiple order items, photos, or wishlist items) are separated into dedicated relational tables (`order_items`, `wishlists`). Repeating groups are eliminated.
  • Second Normal Form (2NF): Satisfies 1NF, and every non-prime attribute is fully functionally dependent on the entire Primary Key. In composite relationship tables (`wishlists`, `order_items`), attributes like `quantity` or `unit_price` depend directly on both keys or the surrogate single key, eliminating partial dependencies.
  • Third Normal Form (3NF): Satisfies 2NF and exhibits no transitive dependencies (i.e., non-key attribute → non-key attribute). In `products`, seller information (e.g., `seller_phone`, `seller_hostel`) is not stored; only `seller_id` is maintained, preserving the dependency `seller_id → phone, hostel` strictly inside `users`.

-- 3. STORED PROCEDURE: Automated Order Completion and Listing Depletion
CREATE OR REPLACE PROCEDURE sp_complete_order_24bce2830(
    p_order_id INT,
    p_operator_reg VARCHAR(15)
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_product_id INT;
BEGIN
    -- Validate operator exists
    IF NOT EXISTS (SELECT 1 FROM users_24bce2830 WHERE reg_no = p_operator_reg) THEN
        RAISE EXCEPTION 'Unauthorized operator: %', p_operator_reg;
    END IF;

    -- Retrieve product
    SELECT product_id INTO v_product_id FROM order_items_24bce2830 WHERE order_id = p_order_id LIMIT 1;
    
    -- Transition Order state
    UPDATE orders_24bce2830 SET status = 'completed' WHERE order_id = p_order_id;
    
    -- Mark product as sold
    UPDATE products_24bce2830 SET status = 'sold' WHERE product_id = v_product_id;
    
    RAISE NOTICE 'Order % completed successfully by Developer/User %', p_order_id, p_operator_reg;
END;
$$;

5. Authentication, Authorization & Security (5 Marks)
5.1 Single Users Table Requirement (Addressing Professor's Key Guideline)

Important Faculty Guideline: Per the assessment instructions on Page 6, "Maintain all users in a single Users table. Do NOT create separate tables such as Admin, Student, Faculty, Manager, Employee."

The database strictly satisfies this rule. A single table users_24bce2830 holds every user record. Role distinctions are handled via an indexed role column with enum constraint ('student', 'seller', 'admin'). Role-Based Access Control (RBAC) middleware checks user.role to conditionally render admin dashboards, item management capabilities, and restricted API routes.

5.2 Authentication Mechanisms & Security Measures
